# Two-Way Issue Tracker Sync (Jira) — Design

**Date**: 2026-08-03
**Status**: Approved, pending implementation plan
**Context**: Third of seven sequenced V1/Phase-1 (P0) gaps, per the original source PRD (`~/Downloads/prd-meridian-qa.md`, §7.4: "Native lightweight issue tracker, plus two-way sync with Jira/GitHub Issues/GitLab Issues"). Builds directly on the public API/webhook infrastructure shipped immediately before this (`docs/superpowers/specs/2026-08-03-public-api-webhook-infrastructure-design.md`) — this project is the first real consumer of that infrastructure's webhook-receiving scaffold.

## Problem

Meridian's native issue tracker (`issues` table) has no connection to any external tracker. The PRD explicitly frames this as necessary so teams migrating from PractiTest (which integrates deeply with Jira) aren't forced to abandon their existing tracker to adopt Meridian.

## Scope decisions

1. **Jira only for this pass**, not Jira+GitHub+GitLab simultaneously. Three different OAuth/API/webhook shapes in one project is too large — this was flagged and decomposed during brainstorming the same way other oversized requests were handled earlier this session. GitHub and GitLab become smaller follow-on projects once this one proves the connection/link/sync pattern. Jira was chosen over GitHub as the first target because it matches the PRD's own positioning (§1): Meridian's target buyer is explicitly a team outgrowing PractiTest, and PractiTest's own strength is deep Jira integration.
2. **Authentication: API token + email, per-org**, not OAuth 2.0 (3LO). Jira Cloud supports basic auth via a personal API token (generated by the user at `id.atlassian.com`) plus their account email. An org admin pastes both into Meridian once. Rejected OAuth 3LO for this pass — it requires registering an OAuth app with Atlassian, building an authorization-code exchange flow, and handling refresh-token rotation, which is meaningfully more engineering for a first integration than the value justifies yet.
3. **Both sync directions**, not Meridian→Jira only. This is what "two-way sync" actually means and is what the PRD requirement is actually asking for — a one-directional version would leave a real gap (a Jira-side status change never reflecting back in Meridian).
4. **Sync is opt-in per issue** ("Send to Jira" action on an existing Meridian issue), not automatic for every issue created. Not every org will want every Meridian issue to spawn a Jira ticket, and blanket auto-sync would work against the PRD's own "don't force teams to abandon their tracker" framing — Jira sync is an enhancement layered on top of a fully usable native tracker, not a mandatory funnel.
5. **Conflict resolution: last-write-wins by timestamp**, not a field-partitioned authority split (e.g. "Jira owns status, Meridian owns everything else"). Simpler, no user-facing conflict UI needed, matches what most lightweight two-way sync tools actually do. Accepted risk: a rare near-simultaneous edit on both sides silently loses one side's change.

## Schema

### `issue_tracker_connections`

One row per org (currently only `provider = 'jira'`, but the column exists for future GitHub/GitLab rows to reuse this same table rather than a Jira-specific one).

```sql
create type issue_tracker_provider as enum ('jira');

create table issue_tracker_connections (
  id uuid primary key default gen_random_uuid(),
  org_id uuid not null references organizations(id) on delete cascade,
  provider issue_tracker_provider not null,
  jira_base_url text not null,
  jira_email text not null,
  vault_secret_id uuid not null, -- references the Vault secret holding the API token
  created_by uuid not null references auth.users(id),
  created_at timestamptz not null default now(),
  unique (org_id, provider)
);

create index issue_tracker_connections_org_id_idx on issue_tracker_connections(org_id);

alter table issue_tracker_connections enable row level security;

create policy "admins can manage tracker connections" on issue_tracker_connections
  for all using (private.is_org_admin(org_id))
  with check (private.is_org_admin(org_id));
```

**Why the token lives in Supabase Vault, not a column**: Meridian's existing `api_keys` table (from the API/webhook project) stores a one-way **hash** — Meridian only ever needs to *verify* a caller's key, never see it again. A Jira API token is the opposite: Meridian needs to retrieve the actual plaintext to call Jira's API on the org's behalf, so it needs real, reversible encryption. Supabase's built-in `supabase_vault` extension exists specifically for this "store a third-party credential, decrypt server-side when needed" case, and is the officially recommended pattern for it rather than hand-rolling `pgcrypto` key management. `vault_secret_id` references the Vault-managed secret; the token itself is written via `vault.create_secret()` and read via the `vault.decrypted_secrets` view, both from a SECURITY DEFINER function — never read directly by RLS-scoped queries.

### `issue_tracker_links`

```sql
create table issue_tracker_links (
  id uuid primary key default gen_random_uuid(),
  issue_id uuid not null references issues(id) on delete cascade unique,
  connection_id uuid not null references issue_tracker_connections(id) on delete cascade,
  external_issue_key text not null,
  external_issue_id text not null,
  external_updated_at timestamptz,
  last_sync_error text,
  created_at timestamptz not null default now()
);

create index issue_tracker_links_connection_id_idx on issue_tracker_links(connection_id);
create index issue_tracker_links_external_issue_id_idx on issue_tracker_links(external_issue_id);

alter table issue_tracker_links enable row level security;

create policy "members can view tracker links" on issue_tracker_links
  for select using (
    private.is_org_member(private.project_org_id((select project_id from issues where id = issue_id)))
  );
create policy "members can manage tracker links" on issue_tracker_links
  for all using (
    private.is_org_member(private.project_org_id((select project_id from issues where id = issue_id)))
  )
  with check (
    private.is_org_member(private.project_org_id((select project_id from issues where id = issue_id)))
  );
```

`external_issue_id` (Jira's internal numeric id) is stored separately from `external_issue_key` (e.g. `PROJ-123`) because the key can change if an issue is moved between Jira projects, while the id is permanent — API calls and webhook payload matching should key off the id, display should use the key. `external_updated_at` and `last_sync_error` are the fields the sync logic reads/writes to implement last-write-wins and surface failures in the UI, respectively.

## Meridian → Jira sync

Triggered by an explicit "Send to Jira" action on an issue (create the link + push), and thereafter by Meridian-side issue updates on already-linked issues. Calls Jira's REST API directly using the connection's decrypted token:
- Create: `POST /rest/api/3/issue`
- Update: `PUT /rest/api/3/issue/{key}`

Field mapping: title → `summary`, description → `description`, severity → Jira `priority` (via a small fixed lookup table, since Jira's default priority names — Highest/High/Medium/Low/Lowest — don't line up 1:1 with Meridian's low/medium/high/critical).

**Status requires a separate mechanism**: Jira does not support setting workflow status via a plain field update on the issue. Status changes go through Jira's transitions API — first `GET /rest/api/3/issue/{key}/transitions` to fetch the *current, workflow-specific* set of legal transitions, then match Meridian's target status to the transition whose target name corresponds, then `POST` that transition's id. This is meaningfully more involved than the other field mappings and gets its own small helper rather than being folded into the generic field-mapping code.

This call happens synchronously right after the Meridian-side database write completes, and never blocks or fails the Meridian save — if the Jira call fails (network error, invalid transition, revoked token), the Meridian issue is still saved, and the failure is recorded in `issue_tracker_links.last_sync_error` for the UI to surface, not silently swallowed.

## Jira → Meridian sync

**The generic webhook scaffold from the API/webhook project doesn't fit Jira as-is.** That scaffold (`src/app/api/v1/webhooks/[source]/route.ts`) assumes HMAC-SHA256-signed payloads (`X-Webhook-Signature` header) — but Jira Cloud's native webhook feature has no such signing mechanism. It supports only a static webhook URL, optionally with a shared secret embedded as a query parameter. Rather than forcing an HMAC assumption onto a provider that doesn't support it, this adds a **dedicated** route, `src/app/api/v1/webhooks/jira/route.ts`. Next.js allows a static path segment to coexist with, and take precedence over, a dynamic segment at the same position (`/api/v1/webhooks/jira` vs. `/api/v1/webhooks/[source]`), so this doesn't conflict with the existing generic catch-all — it's simply the more specific route winning for that one path, exactly as Next.js routing already works for any other static-vs-dynamic collision.

The Jira-specific route: validates the query-param token, parses Jira's webhook payload shape (`webhookEvent`, `issue.id`, `issue.key`, `issue.fields.*`), looks up the matching `issue_tracker_links` row by `external_issue_id`, applies the last-write-wins comparison against `external_updated_at`, updates the Meridian issue if Jira's version is newer, and — to keep the same audit trail the generic scaffold already provides — still inserts a row into `webhook_events` (`source = 'jira'`) regardless of validity, matching that table's existing purpose.

## Where the connection gets configured

New page, `/settings/integrations/jira` (Settings currently has an "Integrations" row that's a pure stub — this becomes its first real sub-page, following the same pattern `/settings/api` established for API keys): a form for `jira_base_url`/`jira_email`/API token (write-only — never redisplayed after saving, same "shown/entered once" principle as Meridian's own API keys), owner/admin only, matching the permission level of every other org-wide connection-type setting in this app.

Per-issue "Send to Jira" and the resulting linked-issue indicator live on the existing issue detail page (`/projects/[projectId]/issues/[issueId]`), not a new page.

## Explicitly out of scope for this pass

- GitHub Issues and GitLab Issues sync (separate, later projects reusing this pattern).
- OAuth 2.0 (3LO) authentication to Jira.
- Field-partitioned conflict resolution (e.g. Jira-owns-status).
- Bulk/backfill sync of pre-existing Jira issues into Meridian, or vice versa — only issues explicitly linked going forward.
- Custom field mapping beyond the fixed title/description/severity/status set.

## Open items for the implementation plan

- Exact Vault API call shapes (`vault.create_secret`, `vault.decrypted_secrets`) and whether `supabase_vault` is already enabled on this project — confirm during planning via `list_extensions` rather than assuming.
- Exact Jira severity↔priority mapping table values — Jira's default priority scheme (Highest/High/Medium/Low/Lowest) needs a specific fixed mapping decided during planning, not left as a vague "map severity to priority."
- The exact webhook query-param token format/length and where an org's per-connection token is generated and surfaced in the `/settings/integrations/jira` UI so an admin can actually configure the webhook URL in Jira's admin panel.
